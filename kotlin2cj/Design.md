# kotlin2cj 技术方案（Design）

> 一个**完全基于自组织/局部规则**的 Kotlin → 仓颉（Cangjie）源到源翻译工具，
> 用 Rust 实现。本文档说明其设计理念、系统架构、局部规则集、自组织引擎与
> 工程实现，对应 `idea.md` 中「把代码翻译视作信息沙堆（Self-Organized
> Criticality, SOC）」的构想。

---

## 一、设计目标与理念

### 1.1 目标
- 把典型的、不同规模的 Kotlin 程序翻译为**可被 `cjc` 直接编译运行**的仓颉代码。
- 翻译过程**不依赖任何集中式神经网络或全局规划器**，而是由大量**只看自己与
  直接邻居**的局部规则自发作用、级联收敛得到全局一致的译文。
- 工具可解释、可增量、可扩展：局部修改只引发有限范围的「雪崩」，无需全局重译。

### 1.2 核心隐喻：翻译即沙堆
| 沙堆模型 | 翻译系统 |
|----------|----------|
| 格子 | 语法单元（声明 / 语句 / 表达式）= 图节点 |
| 沙粒高度 | 节点的翻译状态（是否已确定目标片段、置信度） |
| 局部崩塌规则（高度≥4 向邻居倾倒） | 局部翻译规则（子节点就绪 → 计算本节点译文） |
| 崩塌引发的雪崩 | 状态变更沿语法/依赖边的级联传播 |
| 自组织临界态 | 整张图收敛：任何局部不再主动变更 |

系统是**异步、去中心化**的：没有「翻译主循环按 AST 顺序递归」，而是一个
worklist（活动节点队列）不断弹出「被唤醒」的节点、就地应用局部规则、再把
受影响的邻居重新唤醒，直到队列清空（到达稳定/临界态）。

## 二、系统架构

```
 Kotlin 源码
     │
     ▼
┌──────────┐   Token 流（含字符串模板拆分）
│  lexer   │ ─────────────────────────────►
└──────────┘
     │
     ▼
┌──────────┐   递归下降 + 词法作用域解析
│  parser  │   构建「翻译图」节点 + 语法边 + 依赖边
└──────────┘
     │
     ▼
┌──────────┐   worklist 异步松弛（局部规则 → 崩塌级联）
│  engine  │   每个节点：自身 + 子节点译文 ⇒ 本节点译文
└──────────┘
     │
     ▼
┌──────────┐   从根节点装配 + 按需注入 import
│  emit    │
└──────────┘
     │
     ▼
 仓颉源码（.cj）
```

源码模块（`src/`）：

| 文件 | 职责 |
|------|------|
| `lexer.rs` | 词法分析；把字符串模板 `"...$x...${e}..."` 拆为字面量/插值片段，使每个插值成为独立子图 |
| `node.rs` | 翻译图的数据结构：节点种类 `Kind`、SOC 状态 `State`、语法/依赖边、`children_of` |
| `parser.rs` | Kotlin 子集递归下降解析；Kotlin→仓颉**类型映射**；标识符引用的作用域解析（建立依赖边）；关键字转义 |
| `engine.rs` | **自组织引擎核心**：worklist 松弛（含双向上下文传播）、粒子驱动松弛、兄弟一致性级联、雪崩统计、重命名扰动 |
| `render.rs` | **渲染规则**：从 engine.rs 拆分，包含所有 AST→仓颉代码的局部翻译规则（render/render_binary/render_call/render_class 等） |
| `heuristics.rs` | **类型启发式**：从 engine.rs 拆分，包含 looks_string/looks_char/looks_numeric/provably_non_collection/is_nullable_expr 等类型推断辅助 |
| `main.rs` | CLI：翻译文件、`--stats` 自组织统计、`--demo-avalanche` 雪崩演示、`--soc-analysis` SOC 指标分析 |

## 三、翻译图模型

### 3.1 节点（Node）
每个语法单元是一个图节点，携带 SOC 状态向量：

```
State {
    target:      Option<String>,  // 已确定的目标语言片段（None = 未翻译）
    confidence:  f32,             // 置信度
    conflict:    bool,            // 冲突标志
    version:     u64,             // 版本号（单调递增，防回退/震荡）
    temperature: u32,             // 温度：被触发次数，用于观察活跃度/抑制震荡
}
```

节点种类 `Kind` 覆盖：程序、函数、参数、类、变量声明、名字、块、表达式语句、
赋值、return、if、while、for-range、for-each、when、各类字面量、标识符引用、
一元/二元运算、区间、调用、集合字面量、索引、成员访问、Lambda 等。

### 3.2 边（Edge）
- **语法邻接边**：父子关系。`children_of(node)` 给出全部句法子节点，`parent`
  反向指回。译文「自底向上」沿此边传播（叶子先确定，逐层向上）。
- **依赖边**：标识符引用 → 其声明的 `Name` 节点（`dep`），声明反向保存
  `dependents`。声明改名（如关键字转义、人工修正）会沿此边把所有引用「崩塌」更新。

这正对应 idea.md 的两类边：语法邻接 + 依赖关系。

## 四、局部规则集

规则只依赖**节点自身 + 直接邻居（子节点已确定的 `target`）**，是纯函数
`render(node) -> Option<String>`：当某个必需子节点尚未就绪（`target == None`）
时返回 `None`，该节点保持「未翻译」，等待被邻居再次唤醒——这就是「局部
汇合 / 合流（Church-Rosser）」在工程上的体现：无论唤醒顺序如何，最终译文一致。

主要规则族（详见 `corpus/pairs.md` 的平行语料归纳来源）：

1. **原子类型映射**：`Int/Long→Int64`、`Double/Float→Float64`、`Boolean→Bool`、
   `Char→Rune`、`List/Map/Set→ArrayList/HashMap/HashSet` 等（含泛型递归映射）。
2. **表达式传播**：二元/一元运算用子节点译文组合，必要时按优先级补括号；
   字符串模板把 `$x`/`${e}` 统一成仓颉 `${...}`。
3. **控制流改写**：`until→..`、`..→..=`、`step→ : n`、`downTo→ : -n`；
   `when(x){…}→match(x){…}`（逗号多值 → `|`，`else → case _`）；
   无主语 `when{…}→if/else` 链。
4. **集合字面量**：`mutableListOf(…)→ArrayList([…])`，空集合借显式泛型或变量
   类型标注生成 `ArrayList<Int64>()`。
5. **声明与类**：`fun→func`、`fun main→main`、表达式体函数补 `return`；
   Kotlin 主构造器展开为仓颉「成员变量 + `init` 构造函数 + `this.x = x`」
   （因 `cjc 1.0.5` 不支持主构造器语法）。
6. **关键字转义（命名冲突崩塌）**：与仓颉关键字冲突的标识符用反引号包裹，
   声明与全部引用一致更新。

> 规则集是**预置 + 可从语料归纳**的：`corpus/` 中的最小平行片段对，逐条对应到
> 上述局部模式。新增一类语法只需新增一族「子节点译文 → 本节点译文」的局部规则，
> 不触动引擎与其他规则。

## 五、自组织引擎（核心）

### 5.1 初始松弛（initial relaxation）
```
1. 建立依赖边：所有标识符引用 → 声明，声明登记反向 dependents。
2. worklist ← 全部节点。
3. while worklist 非空：
       id ← worklist.pop_front()
       t  ← render(id)              // 局部规则
       if t == None: continue       // 子节点未就绪，等待再次唤醒
       temperature(id) += 1
       if t != target(id):          // 状态变更（一次「崩塌」）
           target(id) ← t; version(id) += 1
           将 parent(id) 与 dependents(id) 重新入队   // 雪崩传播
4. worklist 清空 ⇒ 到达稳定（临界）态；根节点 target 即整篇译文。
```

叶子节点（字面量、名字）首轮即可确定译文，随后逐层「向上崩塌」，等价于沙堆从
低处向高处的逆向倾倒——这是「表达式传播」规则的自然结果。

### 5.2 防震荡
- **版本号单调递增**：每次状态变更 `version += 1`，不允许回退到旧状态。
- **纯函数 + 子节点译文单调确定**：每个子节点一旦确定 `target` 即不再改变，
  故父节点的 `render` 是单调的，不会反复横跳；`temperature` 记录触发次数，可用于
  观测活跃度并在需要时抑制（当前数据集无震荡发生）。

### 5.3 增量与雪崩（自动修复）
`perturb_rename(name_node, new_name)`：把某个声明改名并清空其 `target`，仅以该
节点为种子重新松弛。变更沿依赖边传到所有引用、再沿语法边上溯到根，**只重算受
影响的子图**，无需全局重译——这正是 SOC 系统「在沙堆上添一粒沙，自动级联修复」
的特性。`--demo-avalanche` 会打印本次**雪崩规模**（级联状态更新次数）。

### 5.4 临界性观测
`--stats` 输出节点数、初始雪崩规模、状态更新总数、累计触发次数。对不同规模程序
重复重命名扰动，可观察到雪崩规模随被引用次数变化的分布——多数扰动只影响少数
节点，少数扰动（改动高扇出的核心声明）引发较大级联，定性符合幂律特征。

## 六、Kotlin 子集与映射覆盖

已支持的典型场景：
- 变量 `val/var`、显式/推断类型、算术/比较/逻辑运算、`++/--/+=` 等。
- 字符串模板（含嵌套表达式插值）、字符字面量、浮点字面量规整。
- `if/else`（语句与表达式）、`when`（主语式 → `match`，条件式 → `if` 链）。
- `while`、`for` + 区间（`..`/`until`/`downTo`/`step`）、`for` + 集合遍历、
  `break/continue`、嵌套循环。
- 函数（块体 / 表达式体 / 递归 / `main`）、命名实参标签剥离。
- 集合：`List/Map/Set` 字面量与泛型、下标读写、`.size`、`.add` 等。
- 类：主构造器（`val/var/普通`参数）、成员变量、成员方法、对象创建、方法/属性访问、
  多类协作、类实例放入集合。

### 6.1 已知差异与边界
- **数值不自动提升**：仓颉不会把 `Int64` 隐式转 `Float64`，故混合算术需源端显式
  统一（与 Kotlin 不同）。
- **浮点打印格式**：仓颉默认形如 `3.140000`，测试期望据此撰写。
- **字符串下标**：仓颉 `s[i]` 取字节（`UInt8`），语义与 Kotlin `Char` 不同，
  数据集回避字符级下标。
- 未覆盖：空安全 `?./?:` 的完整语义、泛型函数、扩展函数、协程、Lambda 高阶链式
  调用（`forEach/map/filter`）等，作为后续迭代方向。

## 七、数据集

- **学习语料** `corpus/`：平行片段对 + 规则归纳表 `pairs.md`，记录每条局部规则的
  来源模式（idea.md 中「从平行语料挖掘局部转换模式」）。
- **测试数据集** `tests/cases/`：126 个端到端用例，覆盖基础、控制流、函数、集合、
  类、经典算法（DP 背包/LIS/零钱兑换/编辑距离/LCS、排序 6 种、BFS/DFS/拓扑排序/Dijkstra、
  GCD/LCM/快速幂/素数筛/矩阵乘法/Kadane/两数之和/罗马数字/回文等 26 个算法题）、
  多类协作、设计模式与不同规模程序（含千行级）。
  每个用例含 `.kt` 输入与 `.expected` 期望标准输出。

测试驱动 `tests/run_tests.py`：构建翻译器 → 翻译 → `cjc` 编译 → 运行 → 比对输出，
汇总写入 `tests/log.md`。当前基线 **126/126 翻译、编译、运行输出全部通过**。

## 八、为何符合「自组织 / 局部规则」范式

| 特性 | 传统大模型 | 传统规则系统 | **kotlin2cj（SOC）** |
|------|-----------|-------------|----------------------|
| 控制方式 | 集中式网络 | 全局规则匹配 | **分布式局部规则 + worklist** |
| 全局一致性 | 额外验证 | 人工维护 | **沿依赖边崩塁自发涌现** |
| 局部修改响应 | 整篇重译 | 重新分析依赖 | **只级联受影响子图（雪崩）** |
| 可解释性 | 低 | 高 | 中（规则简单，级联路径可观测） |
| 规模扩展 | 受上下文长度限 | 受规则完备性限 | **纯局部操作，线性可扩展** |

引擎不持有「整篇程序的全局意图」，每个节点只回答一个局部问题：*「在我的子节点
都翻译好之后，我该长成什么样？」*——全局正确的译文，是这些局部回答相互级联、
自组织收敛的涌现结果。
